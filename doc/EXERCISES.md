# Lab exercises

Use these exercises to learn how Kea HA, DDNS, and PostgreSQL replication behave.
Record the starting state, observed result, recovery time, and any surprises.
These are manual experiments, not evidence that the lab serves a physical LAN.

## Before starting

- Run commands from the repository root against your own lab.
- Start the lab using the instructions in [README.md](../README.md). The commands
  below assume the default mode. In firewall mode, add
  `-f docker-compose.firewall.yml` after `-f docker-compose.yml` in every command.
- Commands that stop or restart services interrupt the lab. Finish each recovery
  step before moving on. Keep volumes, identities, and logs; do not use
  `full-down`, `down --volumes`, or a clean reset for these exercises.
- Examples use POSIX shell syntax. In PowerShell use `curl.exe` instead of `curl`
  for host HTTP requests. Use the existing API username; curl prompts for its
  password. Do not put credentials or keys in your exercise notes.
- DHCP/DNS are not published to the host. The Docker bridge uses
  `192.168.69.0/24` and `fd69:69:69::/64`; configured DHCP client subnets are
  `192.0.3.0/24` and `fd69:69:69:1::/64`. Real DHCP tests require an isolated
  client/relay harness that delivers packets to Kea with the correct subnet
  selection and gives the clients a return path. Attaching a client to the
  existing Docker bridge alone does not establish that setup.
- No client harness is supplied here. If you do not have one, run the status,
  DNS, and replication checks and mark DHCP traffic tests as **not exercised**.

Capture a baseline:

```sh
docker compose -f docker-compose.yml ps
curl --user kea -H "Content-Type: application/json" -d '{"command":"status-get"}' http://127.0.0.1:8100/
curl --user kea -H "Content-Type: application/json" -d '{"command":"status-get"}' http://127.0.0.1:8200/
docker compose -f docker-compose.yml exec -T backups /usr/local/bin/healthcheck.sh
```

Expected: both DHCP4 control endpoints respond successfully; both standby
clusters accept connections and are in recovery. Container health alone does
not establish client service or current replication.

## 1. DHCP peer failure and return

1. With both peers running, use the client harness to acquire and renew leases.
   Record client identifiers, addresses, lease lifetimes, and the responding
   server. Observe both peers' HA state through `status-get` or Stork.
2. Stop one peer:

   ```sh
   docker compose -f docker-compose.yml stop dhcp1
   ```

3. Poll the surviving peer's status and send new client requests and renewals.
   Record the time to communication loss and any subsequent takeover.
   The current configuration uses a 60-second response threshold and
   `max-unacked-clients: 5`; a small number of clients may not trigger takeover.
   Use enough distinct clients to exercise requests assigned to the missing
   peer. Do not interpret one successful renewal as full failover.
4. Restore the peer:

   ```sh
   docker compose -f docker-compose.yml start dhcp1
   ```

5. Observe synchronization and return to load balancing. Repeat requests and
   check that the same address was not assigned to two different clients.

Expected: the survivor detects communication loss; takeover depends on the HA
failure-detection conditions. After recovery, peers synchronize and resume
normal service. Repeat with `dhcp2`, then DHCP6 if the harness supports it.
Stopping `dhcp1` also interrupts its local PostgreSQL primary and Stork agent;
this experiment measures the whole peer container failing.

## 2. DHCP-driven DNS updates

Check D2 control access on both peers, including in firewall mode:

```sh
curl --user kea -H "Content-Type: application/json" -d '{"command":"list-commands"}' http://127.0.0.1:8102/
curl --user kea -H "Content-Type: application/json" -d '{"command":"list-commands"}' http://127.0.0.1:8202/
```

Expected: both return a successful command result. Firewall mode permits these
ports from the same host gateway and management subnets as the other Kea APIs.
Published ports remain loopback-only. ICMPv6 is allowed for neighbor discovery,
router discovery, multicast listener discovery, and IPv6 error handling; this
does not widen the TCP/UDP source allowlists.

1. Acquire a lease with a unique hostname, such as `exercise-01.example.com`,
   using a client that supplies the appropriate hostname/FQDN option. Record
   the actual hostname accepted or generated by Kea and the leased address.
2. Inspect bounded DDNS logs inside the responding peer:

   ```sh
   docker compose -f docker-compose.yml exec -T dhcp1 tail -n 50 /var/log/kea/dhcp-ddns.log
   ```

3. Query the actual hostname and address from a DNS container. Replace the
   example address below with the acquired lease:

   ```sh
   docker compose -f docker-compose.yml exec -T dns1 dig @192.168.69.200 exercise-01.example.com A +norecurse
   docker compose -f docker-compose.yml exec -T dns1 dig @192.168.69.200 -x 192.0.3.100 +norecurse
   docker compose -f docker-compose.yml exec -T dns2 dig @192.168.69.201 exercise-01.example.com A +norecurse
   docker compose -f docker-compose.yml exec -T dns2 dig @192.168.69.201 -x 192.0.3.100 +norecurse
   ```

4. Renew the lease and check that records still agree. If testing release or
   expiry, record when Kea processes removal and when both DNS servers reflect
   it; allow for lease reclamation and zone-transfer timing.

Expected: primary DNS gets the forward and reverse records through Kea D2;
secondary DNS receives them through zone transfer. For IPv6, query AAAA and the
actual IPv6 PTR. An HTTP response from D2 proves control access, not a DNS update.
Without DHCP traffic, SOA queries can check DNS reachability and zone presence,
but do not count them as a DDNS pass.

## 3. Primary outage and replica reconnection

The `backups` container has two independent standbys: leases on port `5432`
follow `dhcp1`; the shared database on `5433` follows `database`.

Docker health checks local readiness and recovery mode, not upstream availability.
Run the healthcheck directly to see streaming status separately:

```sh
docker compose -f docker-compose.yml exec -T backups /usr/local/bin/healthcheck.sh
```

During an upstream outage, `locally ready, streaming disconnected` can coexist
with healthy Docker status. `streaming active` means the WAL receiver reports
`streaming`; it does not prove zero replay lag. The SQL below exposes receiver
status and WAL positions. No receiver row means there is no active receiver.

Inspect both standbys before, during, and after an outage:

```sh
docker compose -f docker-compose.yml exec -T backups psql -h 127.0.0.1 -p 5432 -U postgres -d postgres -c "SELECT pg_is_in_recovery(), pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn();" -c "SELECT status, latest_end_lsn FROM pg_stat_wal_receiver;"
docker compose -f docker-compose.yml exec -T backups psql -h 127.0.0.1 -p 5433 -U postgres -d postgres -c "SELECT pg_is_in_recovery(), pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn();" -c "SELECT status, latest_end_lsn FROM pg_stat_wal_receiver;"
```

1. Stop `dhcp1`. Poll the lease standby until the receiver disappears or no
   longer reports streaming. Confirm that recovery mode can remain true even
   then. Unchanged WAL positions alone do not establish disconnection.
2. Restart `backups` while `dhcp1` remains down:

   ```sh
   docker compose -f docker-compose.yml restart backups
   docker compose -f docker-compose.yml logs --tail 50 backups
   ```

3. Both initialized standbys should start without upstream connectivity. The
   lease standby remains locally ready in recovery while streaming is
   disconnected; the shared standby can continue streaming. Initializing a
   missing cluster still requires its upstream and a successful base backup.
4. Start `dhcp1`, then start `backups` if it exited. Repeat the SQL checks.
   Generate a normal lease change with the harness and observe WAL receipt and
   replay advancing. An idle primary may produce no new replayed transactions;
   elapsed time since the last transaction alone is not a freshness test.
5. Repeat with `database` instead of `dhcp1`. Stopping the shared database can
   also affect DHCP host lookups and forensic logging; record those effects.

Expected: once the upstream returns, streaming reconnects and new WAL is
replayed, provided the required WAL still exists. These are read-only standbys;
this exercise does not promote them or redirect Kea to them.

## 4. Replica recovery after missing WAL

Run this only when willing to replace one standby's contents. Preserve both
primaries and the other standby. A streaming replica is not a historical backup.

1. Prefer an observed missing-WAL failure. Deliberately reproducing one requires
   an isolated disposable copy of the lab and controlled WAL generation; a short
   outage alone may not reproduce it. Do not delete primary WAL files.
2. Record which standby failed, its upstream, and the missing-WAL log message.
   Restore upstream connectivity and confirm reconnecting alone does not fix it.
3. Use the scoped procedure below. Never remove the entire backups volume: it
   holds both `/var/lib/postgresql/lease` and `/var/lib/postgresql/shared`.
4. Normal startup takes a fresh base backup only for the moved cluster. Both
   standbys briefly stop because they share one supervised container; the
   unaffected cluster keeps its data and resumes without being reseeded.
5. Run the SQL checks from exercise 3. Generate a normal change on the affected
   upstream and verify replay. Check that the other standby still streams.

Expected: the reseeded standby catches up from a fresh base backup and receives
new WAL. Record the recovery duration and which replica data was replaced.

### Diagnose before reseeding

```sh
docker compose -f docker-compose.yml logs --tail 100 backups
```

Look for `requested WAL segment ... has already been removed`, and correlate
the message with the lease or shared cluster's upstream address. Use exercise 3
to check recovery mode and receiver status. Connection refused, timeouts, and
authentication errors are not evidence of missing WAL; fix those causes first.
If the required WAL was recycled and no usable archive exists, reconnecting
cannot recover the gap: take a new base backup. Do not delete primary WAL,
promote a replica, or use `pg_resetwal` to bypass recovery.

This lab keeps PostgreSQL's default WAL retention and configures no persistent
replication slots or WAL archive. `max_replication_slots` is capacity, not an
active slot. The initial `pg_basebackup -Xs` WAL stream does not reserve WAL
through later outages. WAL can be recycled before an offline standby catches
up; there is no guaranteed safe outage duration. A future `wal_keep_size`
cushion would depend on WAL generation rate and would not cap total WAL disk
usage. Defaults plus scoped reseeding keep this lab small.
See [PostgreSQL streaming replication](https://www.postgresql.org/docs/15/warm-standby.html#STREAMING-REPLICATION).

### Reseed only the affected standby

These commands run in a POSIX host shell. Ensure the affected upstream is
healthy and capture the logs and SQL evidence first. Set `replica=lease` for
`dhcp1`, or `replica=shared` for `database`. In firewall mode, add the override
file to **every** Compose command, including the helper.

```sh
replica=lease
docker compose -f docker-compose.yml stop backups &&
running=$(docker compose -f docker-compose.yml ps --status running -q backups) &&
test -z "$running" &&
docker compose -f docker-compose.yml run --rm --no-deps --entrypoint /bin/sh backups -eu -c '
  case "$1" in
    lease|shared) data_dir="/var/lib/postgresql/$1" ;;
    *) echo "Choose lease or shared" >&2; exit 1 ;;
  esac
  test ! -L "$data_dir"
  test -s "$data_dir/PG_VERSION"
  saved="${data_dir}.before-reseed-$(date -u +%Y%m%dT%H%M%SZ)"
  test ! -e "$saved"
  test ! -L "$saved"
  mv "$data_dir" "$saved"
  echo "Preserved $data_dir at $saved"
' sh "$replica"
```

Proceed only if all commands succeeded. The helper overrides the entrypoint
and uses `--no-deps`: it only moves the selected directory while `backups` is
stopped. It does not run initialization or PostgreSQL, and it does not start or
modify either primary. Do not run another helper or start `backups` concurrently.
The other standby directory, named volumes, Stork identities, and DHCP logs
remain intact. Keep the preserved directory for diagnosis; it consumes disk
space and is not automatically removed.

Start the existing container using normal initialization:

```sh
docker compose -f docker-compose.yml start backups
docker compose -f docker-compose.yml logs --tail 100 backups
docker compose -f docker-compose.yml exec -T backups /usr/local/bin/healthcheck.sh
```

If the base backup fails, keep the preserved directory and inspect the cause;
do not reset volumes or retry the move blindly. Repeat exercise 3's SQL checks
for both clusters. Confirm recovery mode and active streaming, then generate a
normal change on the affected upstream and observe receive/replay advancement.
Verify the unaffected standby also reconnects. These instructions assume the
fixed backups image is already deployed; source edits alone do not update it.
